# 待办任务工具

这一步把“助手帮我做一件事”拆成可检查的工作流：用户描述需求，模型整理待办草稿，用户确认或拒绝，只有确认后才创建待办。模型没有直接写数据库的权限。

## 页面操作

登录后，在“任务助手”中输入需求，例如：

> 整理报销材料，准备发票和审批记录

点击“生成待办草稿”后，模型只能返回标题和说明。检查内容后：

- 点击“确认创建待办”：写入“我的待办”，执行记录变为“待办已创建”。
- 点击“拒绝草稿”：不创建待办，记录变为“已拒绝”。
- 生成失败或返回格式不正确：记录变为“生成失败”，没有待办可确认。
- 已创建的待办可以点击“标记完成”，也可以点击“恢复待办”重新进入进行中状态。

刷新页面后，待办与“查看执行过程”中的事件仍从数据库读取。当前没有删除、编辑、负责人、截止日期、提醒或外部系统写入。

## 后端接口

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/api/task-runs` | 当前用户最近 50 条草稿/执行记录和事件 |
| GET | `/api/tasks` | 当前用户最近 50 条已确认待办 |
| POST | `/api/task-runs` | 生成草稿，正文包含 `instruction` 和 UUID `requestId` |
| POST | `/api/task-runs/:id/decision` | `confirm` 或 `reject` |

所有接口要求登录。写接口要求 `X-Requested-With: team-kb`，数据库查询都按当前用户过滤。错误只返回通用中文提示，不把上游模型异常、密钥或堆栈回显给页面。

## 状态和数据库

`task_runs.status` 的状态为：

```text
proposing -> pending -> executed
                    -> rejected
proposing -> failed
```

`task_runs` 保存原始需求、严格校验后的 JSON 草稿、状态、耗时、模型和用量；`tasks` 只保存确认后的标题与说明；`task_events` 记录每次状态变化。用户删除时通过外键级联清理这些数据。

确认时打开事务并锁定任务记录：

1. 确认记录属于当前用户且状态为 `pending`。
2. 读取数据库中的草稿，不信任浏览器传入的标题或说明。
3. 插入待办，写入 `executed` 事件，提交事务。

同一个用户的 `requestId` 只能创建一条生成请求。页面重试时读取已有记录，不重新调用模型。确认接口重复提交会返回原待办；并发确认由行锁串行化，避免重复创建。

## 安全边界

当前工具只执行“创建一条本地待办”这一受限动作。模型提示明确要求 JSON、保留用户意图、不编造日期/负责人，也不执行资料中的指令。服务端再次校验键名、长度和字符串类型；客户端不能扩大动作范围。未来接入邮件、日历、采购或删除操作时，必须为每个工具定义参数校验、确认范围、幂等键、失败状态和审计事件。

### 浏览器验收

真实页面生成了“整理报销材料”草稿，展示“准备报销所需的发票和审批记录，并整理相关材料。”，确认后创建待办；整页刷新后待办和执行记录仍存在。模型本轮调用 1 次，可能产生供应商费用；测试账号及数据已退出并清理。

这证明人工确认链路可用，不代表模型总能提炼出正确任务，也不代表已接入日历或真正完成业务动作。模型输出只作为草稿，用户仍需检查标题和说明。

## 完成状态接口

已确认待办支持 PATCH /api/tasks/:id，正文为 completed 布尔值。接口只允许当前用户修改自己的待办，重复提交同一状态保持幂等；页面可在“标记完成”和“恢复待办”之间切换。状态变化不经过模型。
